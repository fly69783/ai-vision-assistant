# 系统架构说明

## 为什么要分层

这个项目会同时涉及网页、接口、图像处理、多个AI模型、语音和测试。如果全部写进一个`main.py`，后面更换模型或定位错误会非常困难。因此基础框架把代码分成五层。

| 层 | 目录 | 用最简单的话解释 |
|---|---|---|
| 接口层 | `app/` | 接收网页上传的图片，把结果返回给网页。 |
| 领域层 | `core/domain/` | 规定“任务、证据、质量、响应”长什么样。 |
| 服务层 | `core/services/` | 决定先做什么、调用谁、怎样排序、怎样播报。 |
| 能力层 | `core/providers/` | 真正调用检测、OCR或视觉模型，可随时替换。 |
| 配置与日志 | `core/config/`、`core/observability/` | 管理阈值、端口和日志格式，不存密钥和原图。 |

## 一次请求怎样流转

```mermaid
sequenceDiagram
    participant U as 网页/用户
    participant A as FastAPI
    participant Q as 质量检查
    participant O as 任务编排
    participant P as AI能力适配器
    participant F as 融合与播报

    U->>A: 图片 + 任务 + 可选问题
    A->>A: 检查格式和文件大小
    A->>Q: 已解码图片
    alt 画面不合格
        Q-->>U: 重拍原因和安全提示
    else 画面合格
        Q->>O: 继续分析
        O->>P: 只调用该任务需要的能力
        P-->>O: 结构化证据/未配置/错误
        O->>F: 去重、计算分数、生成短句
        F-->>U: 状态 + 证据 + 播报文案 + 耗时
    end
```

## 为什么默认能力都是“未配置”

基础框架先证明接口、错误处理和测试方法可以运行。真实模型尚未选定时，`UnavailableProvider`只返回未配置状态，不会随机生成检测框或文字。这可以防止团队在演示和材料中误把占位结果当成真实AI结果。

## 接入模型时不能破坏的约定

1. 每条证据必须标明来源和置信度。
2. 适配器报错时不能让整个服务器崩溃。
3. 不把原始图片写进普通日志。
4. 低置信度信息必须保留不确定表达。
5. 真实模型加入后必须新增对应测试和许可证登记。
